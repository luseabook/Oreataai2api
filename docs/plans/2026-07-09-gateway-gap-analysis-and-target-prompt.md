# 合格生图生视频网关缺口分析与目标模式提示词

## 1. 结论

当前项目已经具备“能提交、能查询、能水合、能展示能力”的基础网关形态，但还没有达到“合格的生产级生图生视频网关”标准。

原因不是单点功能缺失，而是还存在几类会直接影响上线判断的问题：

- 取消任务后，正在执行的工作流可能继续跑完。
- 卡住的 `submitted` 任务缺少明确的退避、过期和回收边界。
- 后台/自动注册类接口存在敏感信息暴露风险。
- 运维底座还不完整，缺健康检查、就绪检查、指标和审计。
- 账号池、模型场景、成本账单、API Key 客户治理还没形成闭环。
- 高级视频场景还缺真实成功样本，不能默认放开。

## 2. 还差什么

### 2.1 任务生命周期

- 取消任务必须真的停止后续执行，不只是改状态。
- `submitted` / `hydrating` 任务要有最大等待时间、重试间隔和回收上限。
- 失败、重试、重新水合要保留 attempt 记录，不能覆盖历史。

### 2.2 安全与审计

- 自动注册/管理接口不能把明文密码、邮箱 token、cookie 直接返回给前端。
- 管理员登录态要有过期时间和强制登出能力。
- 账号敏感字段需要加密存储或最少脱敏展示。
- 关键管理动作要有审计记录。

### 2.3 运维底座

- 需要 `healthz`、`readyz`、`metrics`。
- 需要备份、恢复和升级说明。
- 需要日志分层：请求日志、任务日志、审计日志。

### 2.4 账号池与成本

- 账号需要余额、冷却、失败率、风控状态。
- 调度要先看余额和能力，再决定是否接单。
- 需要真实扣点与估算扣点的对账能力。

### 2.5 模型与视频场景

- `/v1/capabilities` 只是发现，不够，还要有启停和风险控制。
- `reference`、`frame_based`、`motion` 这种高级视频场景不能默认对外开放。
- 视频请求需要明确暴露分辨率、时长、场景等可选项，并和能力表联动。

### 2.6 后台管理

- 任务列表需要分页、筛选、详情、重试、取消、重水合。
- API Key 需要客户归属、限流、日额度、点数额度、白名单。
- 成本页需要按 Key、账号、模型、任务状态拆开看。

## 3. 建议推进顺序

### P0

先修会影响安全和稳定性的点：

- 真取消。
- `submitted` 回收边界。
- 敏感信息脱敏。
- API Key 删除只做软删除。

说明：上述 P0 已在当前工作树中落地，后续不再回头重复推进。

### P1

补齐任务系统闭环：

- 异步任务状态机。
- retry / cancel / hydrate。
- 任务详情和 attempt 记录。

### P2

补齐运营与风控：

- 账号池健康分。
- 余额与冷却。
- 成本对账。
- API Key 配额和客户归属。

当前优先执行的是 P2 的最小切片，而不是一次性补齐全部运营矩阵。

当前最小切片继续向前推进的方向：

- 账号列表导出 derived health/risk/cooling summary。
- 池状态接口补健康统计，支撑看板判断可用账号是否真的健康。
- 任务/用量记录补实际扣点和前后余额快照。
- API Key 引入客户归属，先能列出客户并把 Key 关联到客户。
- `healthz` / `readyz` / `metrics` 已补；下一段回到 P3 的后台 policy patch 路由。

### P3

补齐模型与视频治理：

- 模型/场景开关。
- 高级视频场景真实验证。
- 视频实验室。

最小切片先做：

- `PATCH /api/models/{model_id}/policy`
- `PATCH /api/video-scenes/{scene_id}/policy`

### P4

补齐运维发布能力：

- healthz / readyz / metrics。
- 备份恢复。
- 审计和会话管理。

## 4. 合格网关的验收线

满足下面这些，才能算“合格”而不是“能跑”：

1. 取消后不会继续执行并回写结果。
2. 卡住任务不会无限占用 worker。
3. 前端和接口不会泄漏敏感信息。
4. 能稳定发现模型和场景能力。
5. 视频请求能选择分辨率、时长、场景，并且和能力表一致。
6. 后台能查任务、查账号、查成本、查 Key。
7. 账号池、模型场景、成本、审计形成闭环。
8. 高级视频场景默认受控，真实验证后再开放。
9. 具备最基本的生产运维接口和备份能力。
