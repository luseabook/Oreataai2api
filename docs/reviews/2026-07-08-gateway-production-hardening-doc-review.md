## 结论

前提：实现时必须严格按计划做 TDD，不允许跳过红绿验证；每个任务完成后都要跑对应 targeted test，涉及共享生成链路的任务要跑全量测试。

## 可维护性

结论：通过。

理由：

- 设计没有引入 Redis、Celery、独立服务或新框架，符合当前 FastAPI + SQLite 单体形态。
- 计划把新增逻辑拆成纯 helper：错误封装、请求 hash、能力校验、成本估算、限流配额、账号调度、账号成功/失败标记，避免把所有逻辑堆进 route handler。
- 数据库迁移继续使用 `PRAGMA table_info` 增量列检测，符合当前项目已有迁移方式。
- 成功响应保持向后兼容，只增加字段，不删除旧字段。
- 旧接口 `/v1/task/{task_id}` 保留，新增 `/v1/tasks/{task_id}` 作为标准别名，降低客户端迁移成本。

需要实现时注意：

- `server.py` 已经很大，新增 helper 要按功能分段放置，不要继续把复杂 SQL 和业务规则混在路由函数里。
- 网关错误结构只先覆盖 `/v1/*`，后台 `/api/*` 暂不强行统一，避免前端回归面扩大。

## 边界条件

结论：通过。

已覆盖的关键边界：

- 无能力缓存时，网关生成返回 `503 CAPABILITIES_UNAVAILABLE`，不会盲目转发到上游。
- 非法模型、分辨率、比例、时长、场景返回 `422`，且必须在调用 `CLIENT.create_chat` 前失败。
- `Idempotency-Key` 相同且请求体相同会重放响应，不重复创建任务。
- `Idempotency-Key` 相同但请求体不同返回 `409`。
- API Key 限流和每日请求/点数配额都明确返回 `429`。
- 账号处于冷却期时调度跳过；指定账号也必须满足能力和冷却条件。
- 上游失败会标记账号失败和冷却，避免反复命中坏账号。
- 点数成本无法估算时允许 `null`，不伪造确定成本。
- 任务详情仍按 API Key 范围隔离。

需要实现时注意：

- 能力目录里字段可能是字符串、数字或缺失，实现时要复用已有 `normalize_*` 思路，不要假设所有值类型稳定。
- 每日配额需要明确按服务器本地日期窗口计算；当前项目没有多时区要求，文档接受本地时间。
- 单实例内存限流不适用于多进程部署，文档已明确这是本轮限制。

## 回归风险

结论：通过。

风险控制点：

- 计划要求先做稳定错误 envelope，再做后续校验和配额，避免不同任务各自发明错误格式。
- Schema 任务单独拆出，后续任务可以依赖明确字段，减少隐式失败。
- 所有高风险行为都要求测试证明：不调用上游、幂等不创建第二任务、配额超限、账号冷却、任务隔离。
- 管理后台 UI 更新被放到后段，先完成后端策略和审计，降低前端先行导致的假可用风险。
- 最终验证包含全量 unittest、Python 编译、嵌入 JS 语法解析、`git diff --check` 和未授权 smoke。

需要实现时注意：

- `GET /v1/capabilities` 的 401 行为不能被错误 envelope 改坏。
- 现有 `tests/security_regression_tests.py` 的 16 个测试必须继续通过。
- 不要把真实 `config.json`、`accounts.db` 或任何账号 cookie/密钥纳入提交。

## 审查决定

文档满足进入实现的最低标准。

建议实现顺序保持计划中的 Task 1 到 Task 10，不建议跳到限流或 UI，因为错误结构和 schema 是后续任务的基础。
